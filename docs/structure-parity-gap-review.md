# Structure parity gap review — Minecraft in the browser

Scope: the wiki [Structure](https://minecraft.wiki/w/Structure) page in full — **Overworld**
(underground / above ground / aboveground-and-underground / underwater), **The Nether**, **The End**,
**Structure-like features**, **Removed structures**, **Generation**, and **Data values** (`ID` and
`Tags`). Measured against this repository's world generation (`src/world.js`), its build-template
system (`src/buildings/`, `src/buildingLibrary.js`, `src/buildingStudio.js`), its biome registry
(`src/biomes.js`), its block vocabulary (`src/blockNameMatch.js`) and its loot (`src/mobLootData.js`).

Every prerequisite figure below is produced by
`node scripts/structure-parity/check-prerequisites.mjs`, which reuses the shared block matcher rather
than a private spelling table — the failure mode that `docs/block-parity-gap-review.md` records for
`cobbled_deepslate`.

## The finding, in one sentence

**No wiki structure generates in this world.** 0 of 22 structure articles, 0 of the 34 Java
configured-structure IDs, 0 of the 13 structure tags and 0 of the wiki's three named generation steps
exist; the build system this repository once called "structures" (`src/buildings/*.js`,
`BuildingLibrary`, Building Studio) is a **player- and AI-placed build template** — the opposite
direction of travel from world generation — and the only terrain feature that resembles a wiki
structure at all is one 6×6 hardcoded cottage in chunk (0,0) at
[world.js:1410](src/world.js#L1410).

The second finding was a **naming collision**: a `StructureLibrary` that reads like the wiki's
structure registry, and a `structures/` directory holding decorative player builds (aquarium,
spaceship, castle). A `village_plains` ID, a `/locate structure` command or a structure tag would
have had no home a reader could guess, and an agent asked to "add the desert pyramid to the structure
library" would plausibly have added a placeable template instead of a generator.

**That collision is now resolved (P0, done).** The Studio, its library, its context module, its
template directory, its tests, its DOM ids, its CSS classes, its creative tab, its persisted save keys
and its localStorage keys are all `Building*`; the word *structure* now means only the wiki concept.
The rename is recorded in §8 P0, and the codebase is ready for `src/worldgen/structures/` to be
created as the generated-structure home.

### 1.4 Spawn ecology stands in for structure spawning

Mobs appear from a hand-written menagerie at world start, not from generation or a spawn scheduler:
`spawnVillageMobs()` ([main.js:712](src/main.js#L712)) places fixed offsets per selected biome —

engine "does not implement the whole vanilla biome/light/category-cap/group/despawn/structure system".

## 5. Data values: the identity layer is entirely missing

### 5.1 IDs

The wiki lists 21 rows covering **34 Java configured-structure IDs** (`ancient_city` …
`village_taiga`) and their Bedrock aliases. This repo registers **0**. There is nowhere to put one:
`BuildingLibrary.getBuilding()` ([buildingLibrary.js:113](src/buildingLibrary.js#L113)) matches
build-template names in the *Building* namespace, not structure IDs, and no worldgen module has a
registry. The rename in §8 P0 is what makes those two namespaces distinguishable at all — before it,
`getStructure()` was the build-template lookup.

Consequences that are not cosmetic:

- No `/locate structure` is possible, and no `/place` — the two commands the wiki's opening paragraph
  defines a structure by.
- `treasure_map`, `ocean explorer map`, `woodland explorer map`, `trial explorer map` and the
  eye-of-ender locate are all keyed off these IDs, so cartography and the stronghold hunt cannot be
  built without them.
- Nothing can be saved or migrated by ID, so a generated structure is indistinguishable from terrain
  once the voxels are written (see §6, G11).

### 5.2 Tags

All 13 tags are absent, with one already noted in the docs: `#dolphin_located`
(`docs/dolphin-parity.md:52`). The others — `#village`, `#mineshaft`, `#ruined_portal`, `#shipwreck`,
`#ocean_ruin`, `#eye_of_ender_located`, `#on_treasure_maps`, `#on_ocean_explorer_maps`,
`#on_woodland_explorer_maps`, `#on_trial_explorer_maps`, `#cats_spawn_in`, `#cats_spawn_as_black` —
have no mechanism: there is no structure registry to tag, and no cat/dolphin locate behaviour to read
them.

## 6. Systemic gaps

These are the real work. Each is a *system*, and each is what makes an individual structure cheap
afterwards.

| # | Gap | What is missing | What already exists to build on |
| --- | --- | --- | --- |
| **G1** | Registry & IDs | No configured-structure registry, no ID namespace, no dimension/gate metadata, no `/locate` or `/place` | `BIOMES` registry and the `BLOCKS` id pattern are the template for one |
| **G2** | Placement algorithm | No spacing / separation / salt / spread-type / frequency / weight. The wiki's *Structure set* page defines all six; nothing here places a structure at a computed world position | The tree pass is exactly this shape already: a **global spacing-4 grid in world coordinates with deterministic jitter** ([world.js:1006-1051](src/world.js#L1006)) |
| **G3** | Biome gating | No gate concept | All 118 biome gates the wiki names resolve in `BIOMES` — the registry is ready, only the consumer is missing |
| **G4** | Chunk-population ordering | No population pass at all. Structures whose origin is elsewhere, or that spill into already-generated neighbours, cannot be expressed; the wiki's `TerrainPopulated` flag, `structure_starts`, `structure_references` and `features` steps have no equivalent | Chunk generation is already deterministic and *order-independent* for trees (trunks before canopies, neighbour-drawn canopies) — the one hard property a structure pass needs, already proven by `tests/treePlacement.test.js` |
| **G5** | Cross-chunk writes | `docs/voxel-engine-plan.md:180` records it as a known open gap: "**Structures still cannot span chunk borders.** Trees can now; the structure generators are a separate path and still write within their own chunk." | The tree pass already solves the neighbour problem: every chunk draws every canopy that overlaps it, clipped to itself, so no chunk depends on generation order ([world.js:1006-1066](src/world.js#L1006)) — a structure pass needs the same trick or a real cross-chunk writer |
| **G6** | Terrain adaptation | No `none`/`beard_thin`/`beard_box`/`bury`/`encapsulate` equivalent, no foundation logic. The cottage hardcodes `y = 25`; templates take an absolute `origin.y` | `worldSpawn.js` already scores columns against the terrain (`getHighestSolidY`, hazards, head room) — the primitive a foundation pass needs |
| **G7** | Piece assembly | No template pools, no jigsaw, no structure templates, no block-based piece files | The template model (`generate(origin, params, BLOCKS) -> block list`, [buildingLibrary.js:260](src/buildingLibrary.js#L260)) is the right *shape* for a structure-template applier; it just needs a piece/pool layer and a worldgen caller |
| **G8** | Loot tables | **Zero chest loot tables.** `rollLoot` ([mobLootData.js:85](src/mobLootData.js#L85)) is mob drops. Chests are per-position player storage ([chest.js](src/chest.js)) with no generated contents, so "loot chest" cannot be expressed | The mob-drop roller is a working weighted-roll implementation to generalise |
| **G9** | Spawn overrides | No structure-driven spawning, and no *natural* spawning to override: mobs come from `spawnVillageMobs()` at start-up and from spawn eggs. The wiki's `spawn_overrides` and "wither skeletons and blazes exclusively spawn here" have no carrier | The full mob roster needed by the structures exists (guardian, elder guardian, drowned, shulker, piglin, piglin brute, hoglin, blaze, wither skeleton, cave spider, silverfish, witch, cat, vindicator, evoker, vex, allay, pillager, iron golem, warden, breeze, ender dragon, end crystal) |
| **G10** | World-creation options | No "Generate Structures" toggle and no bonus chest, so the wiki's own distinction between structures and structure-like features cannot be expressed | The world/biome selection UI already exists |
| **G11** | Persistence | The save format stores voxels (`encodeVoxelsRLE`) plus a `builtStructures` record for AI builds only ([mapManager.js:70](src/mapManager.js#L70), [mapManager.js:136](src/mapManager.js#L136)). A generated structure has no record, so it cannot be located, regenerated or migrated after save/load | The record shape (`{id,name,type,min,max,center}`) is already the right one to widen |
| **G12** | Determinism contract | Nothing forbids a future structure pass from calling `Math.random` or from deciding placement from neighbouring chunk contents — the two defects `docs/voxel-engine-plan.md:127` records for trees | 12 determinism tests in `tests/treePlacement.test.js` are the pattern to copy for structures |

### Where the wiki's mechanics actually live

The Structure page's own **Generation** section is short: it says structures generate per chunk after
terrain, keyed by a `TerrainPopulated` flag and a "point of origin", that regeneration on an
already-populated chunk roughly doubles its ore, and that structures may spill into neighbouring
already-generated chunks. The vocabulary people usually expect there — structure sets, spacing,
separation, salt, spread type, weight, jigsaw template pools, terrain adaptation, `spawn_overrides` —
lives on the linked pages *World generation § Structures*, *Structure set* and *Structure definition*.
Any implementation should be scoped against those, not against the summary section alone.

## 9. Verification

Each phase should land with tests in the existing style:

- **Registry** — every ID in `scripts/structure-parity/check-prerequisites.mjs` resolves to a gate, a
  dimension and a placement entry; no gate names a biome absent from `BIOMES`.
- **Placement** — for a fixed seed, the same set of structure positions in forward, reverse and
  shuffled chunk order (the exact contract `tests/treePlacement.test.js` enforces for trees).
- **Population** — no structure writes outside its declared bounding box; a structure straddling a
  border produces byte-identical blocks whether or not the neighbour is generated first.
- **Terrain adaptation** — a structure on a slope has no floating pieces and no blocks below bedrock.
- **Loot** — every chest position a structure declares yields only items that exist as an item or a
  block (the check the audit script already performs for the prerequisite list).
- **Save/load** — a generated structure is locatable after a round trip, and loading twice does not
  duplicate it (the wiki's own warning: repopulating an already-populated chunk roughly doubles its
  ore).
